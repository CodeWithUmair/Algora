## 1. What this project is

A NASDAQ-100 scalping bot mechanizing **Fabio Valentini's discretionary order-flow strategy** (originally NQ futures + Interactive Brokers + real Level 2/footprint data) onto **MetaTrader 5** trading **`USTECm`**. Built 2026-09-13 as a sibling to the XAU/USD gold scalper (`../VWAP-EMA-BOT`), reusing its proven architecture (background-thread live engine + Streamlit dashboard + `st.fragment` real-time updates + circuit breakers + SQLite storage) with a completely different strategy engine.

**Read `STRATEGY_SPECIFICATION.md` before touching the strategy code** — it has the full mapping from the guide's discretionary concepts to what's actually mechanized, and is explicit about which parts are approximations (nearly all of them — MT5 doesn't give real order-flow data) vs. genuinely missing (0DTE options sentiment, not implemented at all).

**Update (2026-09-18): this `GOLD` branch now runs BOTH bots as one live process, not just NASDAQ.** The gold scalper (`gold_strategy.py`/`gold_live_engine.py`) was merged into this same repo/branch at some point after the paragraph above was written — it's no longer a separate sibling repo the way `../VWAP-EMA-BOT` implies. `trading_bot/run_live_auto_bot.py` is the actual live entrypoint: it starts `LiveTradingEngine` (NASDAQ, `USTECm`) and `GoldLiveTradingEngine` (Gold, `XAUUSDm`) as two background threads in one process, against one shared MT5 connection, distinguished by magic number. See §7's 2026-09-18 entry for the full detail — that's the current, authoritative state of how this bot actually runs, don't assume single-strategy from the paragraph above.

## 4. Key design decisions (and why)

- **MT5 over Interactive Brokers** — matches the existing proven stack, one broker/terminal for both bots, at the cost of no real order-flow data. User's explicit choice when asked (2026-09-13).
- **Full auto-trader over decision-support dashboard** — the guide is discretionary, but user chose full mechanization, same as the gold bot's model. User's explicit choice (2026-09-13).
- **Range bars from M1 OHLC, not real ticks** — `mt5.copy_ticks_range()` exists and `fetch_ticks_range()` is wired up in `mt5_bridge.py`, but tick history depth on this broker/account is unreliable (same kind of retention limit that capped the gold bot's M1 history to ~2-3 months — see gold bot's `HANDOFF.md` §5 session log). M1-approximated range bars (documented intrabar-path heuristic in `strategy.py`) are the dependable default.
- **Fixed 0.1 lot sizing, not risk-based** (changed 2026-09-14 - `calculate_position_size()`/risk-based sizing was the original design here, matching the guide's asymmetric-dollar-risk framing, but the user explicitly chose a fixed lot sized to the real $100 demo account instead). **This went back and forth within the same day - see §7's "Lot size record corrected" entry for the full story before touching this value again.** Short version: the broker's real minimum is 0.05 (confirmed live via `symbol_info()`); the user was shown both 0.05 and 0.1 backtested side by side (same 177 trades, same 42.9% win rate/PF 3.01 - lot size doesn't change those ratios - but 0.1 nets $395.49 vs $197.74, at 8.44% vs 4.87% max drawdown) and explicitly chose 0.1. That comparison wasn't persisted to the repo at first (chat-only), which made 0.1 look "unverified" to a session that could only see committed files - it briefly got reverted to 0.05 on that basis before being corrected back to 0.1 once the comparison was properly saved as `run_backtest_risk_capped.py`'s `LOT_SIZES` list + `BACKTEST_REPORT.md`'s "Lot size comparison" section. **0.1 is the current, correct, evidence-backed value** - don't re-revert it without reading §7 first. `calculate_position_size()` still exists in `strategy.py` and is unit-tested, just no longer called by the live engine - don't assume it's dead code if reused elsewhere later.
- **Daily loss cap ($10), profit deliberately uncapped** (changed 2026-09-14) — `live_engine.py`'s `CircuitBreakerConfig.max_daily_loss_usd` is 10.0 (was an untested 15.0), and the daily *profit* lock (`enable_daily_profit_lock`) that used to silently stop new trades once up $15/day is now **off**. User's explicit design: stop the bot for the day on a loss, never cap a winning day. Every backtest number in `BACKTEST_REPORT.md` assumed profit-uncapped; the live engine didn't match that until this change.
- **0DTE options sentiment: not implemented.** No data source connected. Don't let a future session assume this filter exists just because the guide mentions it prominently.

Don't restart it, don't redeploy it, and don't assume it needs setting up again without first asking the user whether it's still running.** This entry is long because almost everything in it was new ground (first real VPS deployment that actually succeeded) or a real bug, not narration for its own sake.

**Context / why this happened now:** the previous VPS attempt (see the 2026-09-14 entry below, "Current bot performance summary + Azure VPS attempt") was handed off to a friend and never fully resolved from this repo's side. The user reported that whatever VPS the friend set up had MT5 unable to connect to the network, and rather than keep debugging someone else's half-known setup, the user deleted it and provisioned a **brand-new Windows Server 2022 Datacenter VPS** (not Azure this time - a different provider, reached only by the user's own RDP session; this session never had direct network access to it, see the "How this session actually worked" note near the end). This entry is the full bootstrap of that new box, done entirely by the user pasting terminal screenshots/output and this session giving back exact commands - genuinely slower than direct access, but it worked.

**Architecture question resolved: single process, two engine threads, one MT5 connection, not two separate bot processes.** The user asked explicitly whether running NASDAQ and Gold against the *same* MT5 account should be two separate bot instances or one bot handling both. Answer given and confirmed correct against the actual code: `trading_bot/run_live_auto_bot.py` *already* implements the right pattern (built before this session, not new) - both `LiveTradingEngine` and `GoldLiveTradingEngine` run as daemon threads inside one Python process, sharing a single `mt5.initialize()` connection (the MetaTrader5 Python package really only manages one terminal connection cleanly; two separate processes would just contend for the same terminal instance for no benefit), and each engine's orders are tagged with a distinct magic number (gold `9212001`, NASDAQ `9312001`, per §3/§4) so they're fully attributable even though it's the same account. This is the same proven shape as the sibling gold bot. **No architecture change was needed - the existing design was already correct**, this was a confirm-and-explain, not a rebuild.

**Real bug #1 - trade history wasn't actually separated per strategy despite the magic numbers.** `run_live_auto_bot.py` was passing the exact same `db_path` string (`"nasdaq_trades.sqlite"`) to *both* engine constructors - so despite different magic numbers keeping MT5-side positions distinguishable, both engines' SQLite trade logs were being written into one shared file, silently merging NASDAQ and Gold history together. This directly contradicted what the user wanted ("both DB sqlite for different instances" - their words). Fixed: NASDAQ engine now gets `nasdaq_trades.sqlite`, Gold engine gets `gold_trades.sqlite` (`trading_bot/run_live_auto_bot.py`, commit `f508250`). One-line-per-engine fix, no schema change needed since `BotStorage` already takes `db_path` as a constructor param - the bug was purely in the caller.

**Real bug #2 - `mt5_bridge.py` couldn't even be imported, at all, on a clean install.** Once the VPS had Python + `requirements.txt` installed and the repo cloned, the very first `python trading_bot/run_live_auto_bot.py` crashed immediately with `NameError: name 'pd' is not defined` pointing at `mt5_bridge.py`'s `fetch_recent_dataframe()` method signature (`-> pd.DataFrame`). Root cause: `pandas` was never imported at module level in `mt5_bridge.py` - it was only ever imported *inside* that one function's body (and even there, after the line that already referenced `pd.DataFrame()` on an early-return path, so it was broken two ways). Function return-type annotations are evaluated when the class body executes, not lazily, so `pd` had to exist in module scope the moment `class MT5Bridge:` was defined - it never did, so **the entire module failed to import**, meaning this bug would have hit *any* fresh environment running this file, VPS or not; it just happened to surface here because this was the first clean install since whenever that annotation was added. Fixed by adding `import pandas as pd` to the top-level imports and deleting the now-redundant in-function import (`trading_bot/mt5_bridge.py`, commit `e8e42d8`). Confirmed fixed by a plain local `from trading_bot.mt5_bridge import MT5Bridge` import check before pushing, then confirmed again for real on the VPS after `git pull`.

**New file: `scripts/setup_vps.ps1`.** Written mid-session as a one-shot bootstrap (Chocolatey → Python/Git → clone → checkout `GOLD` → `pip install -r requirements.txt`) for standing up a fresh Windows box faster next time. **Caveat, important: it was never actually completed successfully on this VPS** - the Chocolatey bootstrap step hung for 10+ minutes with no progress (installing Chocolatey itself, before it even got to Python/Git) and was killed. What actually worked instead, and is the real, tested path: download the official Python 3.12 installer directly from `python.org` and the latest Git-for-Windows installer via the GitHub releases API (`api.github.com/repos/git-for-windows/git/releases/latest`), run both with silent-install flags (`/quiet InstallAllUsers=1 PrependPath=1` for Python, `/VERYSILENT /NORESTART /SUPPRESSMSGBOXES` for Git) via `Invoke-WebRequest` + `Start-Process -Wait` in PowerShell - no Chocolatey involved. This worked cleanly on the first try. **If a future session reaches for `scripts/setup_vps.ps1` again, know that its Chocolatey path is unverified/possibly unreliable on this class of VPS - the direct-installer approach in this entry is the one with actual evidence behind it.** Worth rewriting the script to use that approach instead before trusting it blind next time, rather than assuming the hang was a one-off.

**A genuine trap worth flagging explicitly: PATH doesn't update in an already-open terminal.** After installing Python/Git, running `git --version`/`python --version` in the *same* PowerShell window that was open during install kept failing with "not recognized," repeatedly, even though the installs had actually succeeded (confirmed via `Test-Path`/`Get-ChildItem` against their install directories).
